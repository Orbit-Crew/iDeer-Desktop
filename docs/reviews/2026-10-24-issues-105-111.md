## 关键发现

### 1. P1：#105 的成功上传路径与真实 Server 路由不匹配

Desktop [platform_chat.py:403](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/local-runtime/core/platform_chat.py#L403) 向 `POST /api/threads/{thread_id}/artifacts` 提交 JSON/base64、Idempotency-Key，期待平台 Artifact 回执。

Server [artifacts.py:333](https://github.com/Orbit-Crew/iDeer/blob/6a819f3a73dfc2bda5c097e82b47737c9c1058bc/backend/app/gateway/routers/artifacts.py#L333) 和 [artifacts.py:479](https://github.com/Orbit-Crew/iDeer/blob/6a819f3a73dfc2bda5c097e82b47737c9c1058bc/backend/app/gateway/routers/artifacts.py#L479) 注册的是带路径的 GET/PUT，没有该 POST 集合路由。现有 [devices.py:438](https://github.com/Orbit-Crew/iDeer/blob/6a819f3a73dfc2bda5c097e82b47737c9c1058bc/backend/app/gateway/routers/devices.py#L438) 是设备 grant 后 multipart upload，返回 `local://`，不能等同于本票的平台 Artifact 登记合同。

[#105 报告:24](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/docs/acceptance/issue-105/report.md#L24) 明示使用 deterministic Server fixture；[报告:79](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/docs/acceptance/issue-105/report.md#L79) 也要求真实 Server 合同及跨仓运行通过后才能组织级关闭。缺少 T105-02 的真实 A 上传、D2 下载算 hash，以及 T105-03 的真实越权下载拒绝。

建议复用并对齐既有 grant/Artifact 机制，完成平台登记与权限合同后，重跑 T105-01–04。

### 2. P1：#107 / #110 在线请求不兼容项目固定的 Electron 22

[updates.ts:138](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/src/main/updates.ts#L138) 和 [compat.ts:98](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/src/main/compat.ts#L98) 直接调用全局 `fetch`。项目固定 Electron 22.3.27，主进程 Node 16.17.1；现有 Node 16 banner 没有提供 fetch。

本次使用该 Electron 二进制、加载同一 banner 后直接运行源码转译得到的 `checkOnline`，实测输出：

```json
{"electron":"22.3.27","node":"16.17.1","fetch":"undefined"}
{"actualCheckOnlineError":"fetch is not defined"}
```

现有 Vitest 在外部 Node 运行，无法验证 Electron 内的全局 API。应使用兼容 Electron 22 的请求实现，并在真实主进程验证更新检查和兼容声明刷新。

### 3. P1：#108 的 UI 安装入口没有接通载荷或安装包

[index.ts:163](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/src/main/index.ts#L163) 在线检查只返回摘要，没有保存 `lastPending`；首次在线检查后点击安装会得到 `UPDATE_NOT_STAGED`，代码也没有下载补丁载荷。

离线导入会保存 pending，但 [index.ts:227](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/src/main/index.ts#L227) 只传入 programRoot，没有 coordinator 要求的 payloadRoot / installerPath。[installer.ts:90](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/src/main/installer.ts#L90) 因此拒绝 patch/full。

直接以 UI 同款 options 调用真实 coordinator，分别得到 `UPDATE_PATCH_ROOTS_UNAVAILABLE`、`UPDATE_FULL_INSTALLER_UNAVAILABLE`，没有进入 apply/launch。单测自行补足 options，所以没有发现接线错误。

### 4. P1：#108 的安装布局、停止顺序及重启行为不满足工单

[electron-builder.yml:14](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/electron-builder.yml#L14) 使用 asar，主程序位于 `resources/app.asar` 内；Runtime 位于 `resources/runtime`。但 [index.ts:152](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/src/main/index.ts#L152) 将 resourcesPath 当作根，补丁只允许 `out/`、`resources/` 路径。即使补齐参数，也会写入 `resources/out/...` 或 `resources/resources/...`，没有替换实际运行文件。

[installer.ts:90](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/src/main/installer.ts#L90) 先 apply/launch，再等待并 quit。真正的 runtime.stop 在 [index.ts:36](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/src/main/index.ts#L36) 的 before-quit，无法满足“确认相关进程停止后才替换”。没有 app.relaunch 或对应外部重启步骤，patch 成功也只退出。

应统一正式安装布局，使用进程外协调器，先确认停止，再安装、重启及执行 Runtime 健康任务。

### 5. P1：#109 不能恢复中途复制失败，恢复状态还指向错误备份

[index.ts:216](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/src/main/index.ts#L216) 生成备份 stamp，[index.ts:229](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/src/main/index.ts#L229) 另取 Date.now 生成恢复 stamp。两者之间 coordinator 必等 1500ms，下次启动按后一个 stamp 查找备份会找错目录。

恢复记录只在 outcome.installed 后写入。应用到一半失败或进程中断，没有已持久化的恢复事务。临时目录实测在第一个文件 old→new、第二个 copyfile 失败后，coordinator 返回 failed 并 abort drain，第一个文件仍为 new，没有恢复，留下部分更新。

应在任何替换前落盘同一事务标识及恢复记录，中途失败必须恢复完整程序组合，恢复失败保持停接任务和人工修复状态。

### 6. P1：#109 的版本字符串比较不能证明组合及数据安全

[recovery.ts:113](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/src/main/recovery.ts#L113) 的重启验证只比较 Desktop/Python 版本字符串，没有验证程序/Runtime hash、实际 Runtime 启动和受控任务，也没有当前数据格式对旧程序的可读性门禁。[#109 报告:41](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/docs/acceptance/issue-109/report.md#L41) 以“用户数据未被恢复代码修改”推导旧版能读，不覆盖新版启动迁移数据后再回滚的情况。

应保存并验证完整组合、数据格式兼容声明和真实健康检查；不兼容时保留数据及诊断并要求人工修复。

### 7. P1：#110 单能力门对真实命令不生效，协议不兼容会放行

[compat.ts:78](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/src/main/compat.ts#L78) 仅在 send 携带 capability 时才阻断。但 [ChatCommand:108](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/src/shared/desktop.ts#L108) 的 send 没有该字段，[runtime.ts](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/src/main/runtime.ts) 的字段白名单还会拒绝该字段，实际任务能力由后续模型/Server 派发决定。upload 动作也不经过对应能力阻断。

[compat.ts:65](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/src/main/compat.ts#L65) 遇到更高 minProtocol 返回 declaration:null；[index.ts:97](https://github.com/Orbit-Crew/iDeer-Desktop/blob/ec71f22860820e34855ee4e9bf741d46b3995563/src/main/index.ts#L97) 保存 null，而门逻辑对 null 放行。

本次直接加载当前源码，实测三种情况均未阻断：禁用 local.files.write 后的真实 send、禁用 local.artifacts.upload 后的 upload、签名有效但 minProtocol=2 的核心不兼容声明。

应在 Server 派发及 Runtime 执行前使用可信 capability 检查有效兼容状态，并让核心协议不兼容明确停止新任务。保留历史与回执路径。
