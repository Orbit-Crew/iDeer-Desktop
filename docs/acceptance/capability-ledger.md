# 三层验收记账与六态场景库（#89）

[总规格 #70](https://github.com/Orbit-Crew/iDeer-Desktop/issues/70)（地图 [#51](https://github.com/Orbit-Crew/iDeer-Desktop/issues/51)）要求全量能力等价验收。
本框架把每项能力的验收拆成三层分开记账，并为每项能力的场景行为提供六态记录位。
**机器可读账本 [capability-ledger.json](capability-ledger.json) 是单一事实源**；本文只定义词汇与规则，不复制行数据。

## 能力清单推导（46 + 2 = 48）

#70 名下共 **48 个编号子票**（一期·1 … 六期·48）。其中两张是治理/收尾项而非产品能力：

| 票 | 定性 | 依据 |
| --- | --- | --- |
| #89（六期·48） | 治理 | 本记账框架自身 |
| #120（六期·47） | 治理 | Win7 能力矩阵与专项收尾；其验收标准自述"覆盖全部 46 项能力"，即 #120 在 46 之外 |

由此：**能力 46 项 + 治理 2 项 = 48 行**，全部入账，一个不隐藏。#88（第三方资源核验）虽偏治理性质，
但按上述算术（48 − #89 − #120）落入 46 项能力之内，故本账本按能力行记录、其原版入口按"治理性能力"如实标注。
编号与 GitHub 工单号的对照、每行的中文标题均以 JSON 为准（校验器内嵌同一权威枚举，两者不一致即报错）。

## 三层记账定义

每行三层各自独立记账、各自给证据；**上一层通过不暗示下一层**。

| 层 | 问题 | 状态词汇 | 判定与证据规则 |
| --- | --- | --- | --- |
| 入口恢复 | 原版入口是否指认并恢复到 Desktop 新路径 | 已恢复 / 占位 / 未迁移 / 未记录 / 不适用 | `已恢复`：有跟踪文档（移植记录、专票报告）指认原版入口文件/目录与 Desktop 路径；`占位`：入口位置以如实占位保留、能力未接线；`未迁移`：能力清单明示暂缓/不随包；`不适用`：治理行专用 |
| 业务接线 | 实现面是否存在且有自动化覆盖 | 已接线 / 未接线 / 未记录 / 不适用 | `已接线`：实现面在 develop 树内，且引用至少一个存在的证据路径（专票验收报告优先，其次为明确标注该票号的自动化测试文件）；`未接线`：有跟踪文档明示未接线 |
| 实际候选验收 | 安装候选包上的真实验收 | 已验收 / 部分验收 / 未执行 / 未记录 / 不适用 | `已验收`：绑定候选（安装包哈希等）的场景通过记录；`部分验收`：候选上部分场景通过、部分未执行/未完成；`未执行`：有跟踪文档明示未执行（如"未跑 dist:win/安装包"）；`未记录`：无任何安装层记录 |

通用规则：

- `未记录` 层必须零证据；其余状态**至少一个证据路径且路径必须在树内存在**（校验器强制）。
- `原版入口`、`新路径`、`允许差异` 三个字段允许如实写 `待补`；**宁可待补，不可编造**。允许差异只从移植记录/专票报告里挖，挖不到就待补。
- `lastVerified`：优先取证据自身的报告日期（front matter 的 last-verified 或执行日期）；仅有树内核对的证据（如测试文件存在性核对）取核对日。
- 证据指向旧记录时，沿用 README 的提醒：先读该记录的候选绑定与覆盖范围，再决定能否用于更新代码。

## 六态场景库

每项能力的场景行为按六态记录；六态描述**单个场景的观测结果**，不是通过率：

| 态 | 定义 | 反例（不得记此态） |
| --- | --- | --- |
| 成功 | 场景按预期完成，且断言钉住了预期事实 | 只"没报错"而无事实断言 |
| 拒绝 | 系统按设计拒绝（权限、越权、超限、格式、取消等），给出固定类别且无副作用 | 意外崩溃或静默吞掉 |
| 失败 | 故意注入/构造的失败路径被如实暴露（固定错误码、不伪造成功、视图不丢） | 失败被掩盖或伪造成成功 |
| 断线 | 平台断线语义按设计呈现（显式暂停、在途结果未知、输入锁定） | 断线被静默当作成功 |
| 停止 | 停止/退出语义按设计执行（真退出排空、任务停止、账本清理） | 停止后仍有效应 |
| 恢复 | 重启/重连/重试后按设计恢复（布局恢复、自动恢复播报、有界重试） | 恢复后状态错乱 |

`未执行` 是第七个合法值：场景有记录位但尚无证据。场景槽随证据落地逐项填充；无证据的行为空数组（等价全部未执行），
**不得**为了凑六态而填无证据的态。一期十行是填法示范（见文末）。

## 工单关闭状态解耦（硬规则）

**"工单关闭"不计入任何一层证据。** 账本各行只认树内证据文件；GitHub 工单的 open/closed 状态不是证据字段，账本不记录它。
对照说明（2026-11-08 时点，均为已归档事实）：

- **工单已关 ≠ 实际候选验收已过**：#71 已关，其报告明确只认第一层（入口恢复）、"未执行打包安装器运行"；#77/#79 已关，仅有工作树证据，无安装候选记录。账本相应行候选层记 `未执行`/`未记录`。
- **工单已关 ≠ 安装验收通过**：iDeer 仓 #112–#123 十二票关闭后，[2026-10-30 纠错记录](corrections-2026-10-30-issues-112-123.md)按归档 result.json 重评为 9 incomplete + 2 failed + 1 passed。关闭动作没有让任何场景变通过。
- **工单未关 ≠ 无证据**：实现分支未并入 develop 的行（如 #98、#103、#118、#119）记 `未记录`，与工单开闭无关；并入并留下证据后即升级。

账本行因此可以与工单状态长期不同向；重开/重关工单不要求改账本，改账本只要求新证据。

## 更新协议（随每期候选包更新）

1. 每期候选包验收跑完后，**只更新该候选实际触达的行**：三层状态、六态槽、lastVerified 按证据刷新；
   未触达的行不动。禁止批量把 `未记录` 翻成其他值。
2. 更新时在证据里绑定候选事实（安装包 SHA-256、分支 HEAD、执行日期），绑定载体是各专票报告/
   [final-candidate-binding.md](final-candidate-binding.md) 一类记录文件；账本行引用它们而不复制哈希。
3. `原版入口`/`允许差异` 的 `待补` 随移植记录/专票报告补齐而补齐，同样只引证据。
4. 每次更新跑 `npm run verify:ledger`；校验不过不得合入。

## 校验

```powershell
. .\scripts\project-env.ps1   # 直接调工具时先初始化环境
npm run verify:ledger         # 校验 schema、枚举、证据路径存在性、48 行完整性、一期引用
npx vitest run test/capability-ledger.test.ts   # 校验器失败模式测试（内存夹具，不动仓库树）
```

CI 接入是后续工作（本票不动 workflow 文件，避免与并行分支冲突）；当前以本地与 vitest 运行为准。
